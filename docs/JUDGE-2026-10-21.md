## Findings, worst first

1. **Phantom bids pass every verifier.** The circuit takes any eight public commitments. Every
   checker only compares the first `valid.length` slots with the on-chain memos:
   `packages/service/src/audit.ts:43`, `packages/mcp/src/tools.ts:119`,
   `packages/service/src/testnet-run.ts:218`. Nobody checks that the remaining slots are the empty
   commitment `Poseidon(auction_id, 0, 0)` or that `winner < valid.length`. An auctioneer can put an
   invented bid with no deposit behind it in slot 3 and prove it wins. `verify_result` then reports
   `proof_verifies: true, commitments_match_chain: true` (with `winner_deposit: null`), and
   `audit.ts:45` crashes on `valid[pub.winner].txid` instead of failing a check. The dashboard checks
   only the Groth16 equation (`packages/dashboard/src/App.tsx:178`).
2. **The audit trusts the auctioneer's list of deposits.** `audit.ts:23-24` and `tools.ts:55`
   decrypt only the txids that the auctioneer chose to publish in `deployments/testnet.json`. An
   auctioneer can drop a deposit (and so a bid) from the list, and the audit still prints
   `all checks pass`. The claim "anyone with the auction's incoming viewing key can read every deposit"
   (README "How it works" step 4) is true of the key, but none of the tools checks it.
3. **A bidder who never reveals breaks the auction.** `decide()` leaves out valid deposits that have
   no reveal (`packages/service/src/auction.ts:127`). The proof then covers fewer commitments than
   there are valid deposits, and the auction's own audit check (`audit.ts:43`) fails. One no-show
   deposit makes an honest auction impossible to audit. The record has no field saying which
   deposits went unrevealed, so a bidder whose reveal was ignored has nothing to point at.
4. **The MCP `bid` tool will deposit into a closed auction.** `tools.ts:80-93` checks the bid range
   but not the chain height against `closeHeight`. An agent bidding after the close loses the use of
   its deposit until the auctioneer refunds it.
5. **There is a hardcoded txid in the run script.** `testnet-run.ts:61` reads the chain tip by
   decrypting a fixed, unrelated txid (`6afa0038…`). That is a hardcoded value in a runtime path, and
   it breaks if that transaction is ever pruned from the server's view.
6. **The service declares a binary that does not exist.** `packages/service/package.json:15-17`
   declares `"bin": {"sba": "dist/cli.js"}`, and there is no `cli.ts`.
7. **The dashboard shows a vk hash it never checks.** `App.tsx:224-227` prints
   `verificationKeySha256` from the record, which was itself a constant
   (`testnet-run.ts:236`). The page never hashes the key it actually verifies with.
8. **Only one output per deposit is read.** `audit.ts:27`, `tools.ts:59`, `testnet-run.ts:171`
   take the first output with a text memo. A transaction that pays the auction twice is read as a
   single deposit, and the second note is never refunded. This is documented below, not fixed.

## Weak, misleading or overclaimed statements

- README intro: "pays the seller and **refunds everyone else**". The memo-mismatch deposit
  (`76b0b9bb…`, 100,000 zat) was not refunded, which is by design per `packages/docs`. The unspent
  part of the 60,000 zat fee budget also stays with the auctioneer. It should say "every other
  revealed deposit".
- README "How it works" step 2: "it privately reveals (bid, salt, refund address) to the
  auctioneer". No reveal channel exists. In the live run, `testnet-run.ts:184-186` holds every
  bidder's opening and plays all the roles. This needs to be stated.
- README: "The losing bids appear nowhere: not in the proof, on the chain, in the run record". That
  holds for `deployments/testnet.json`. The gitignored `.demo/auction-state.json` (the auctioneer's
  working state) does hold them, as the auctioneer necessarily does.
- `packages/docs` threat model: "If it withheld a reveal ... the bidder would hold the opening that
  proves a valid deposit was left out." In fact, as finding 3 shows, any unrevealed deposit makes the
  audit fail, honest or not, and the record has nothing a bidder could point at.
- Dashboard "Audit it yourself" step 2 says the proof's commitments are "exactly the valid deposits'
  memos". The tools check a prefix, not "exactly" (finding 1).
- README packages table: "results page: ... in-browser proof verification". That is true, but the
  page verifies only the pairing equation, not that the proof is about these deposits.

## One bold idea

**Reveal by shielded memo to a second, unpublished address, with on-chain censorship evidence.**
Each auction would publish two addresses: the deposit address (its UIVK public) and a reveal address
(its key private to the auctioneer). After the close, a bidder sends a 1-zat shielded note to the
reveal address with memo `sba1r:<auction>:<bid>:<salt>:<refund UA>`. The reveal is then timestamped
on-chain and readable only by the auctioneer. If the auctioneer lists that deposit as `unrevealed`,
the bidder publishes the reveal txid and the auctioneer's own viewing key for the reveal address
can be compelled (or escrowed with a third party) to prove the reveal arrived before the deadline.
That turns "the auctioneer is trusted to collect reveals" into "the auctioneer is caught if it
drops one", with no contracts. Not built here.

## Not fixed (documented)

- Single-party trusted setup: needs a ceremony or a transparent proof system.
- The auctioneer learns every bid at the reveal (inherent to this design).
- One output per deposit transaction (finding 8).
